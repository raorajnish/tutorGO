# TutorGO — Full Feature List (Detailed)

> Every feature currently built in the product, end to end, with the actual mechanics — not just names. Generated 2026-09-05 from a direct survey of the codebase (navigation, every route file, the full Prisma schema, and every `changes-phaseN.md`'s own status table), plus first-hand knowledge of everything built and live-verified in this session (Phases 12–14). For *why* something was built a particular way, see the referenced `changes-phaseN.md` §N.M; for the cross-cutting rules that shape all of this, see `handoff.md`.
>
> Legend: 🟢 built & verified live · — not built (see `progress.md` §3 for why, in one line each)

## 1. Platform layer (SuperAdmin)

A fully separate console — its own login (`SUPERADMIN` role, platform-seeded, never invited), its own nav section, and no route in this layer accepts an `instituteId` from a normal staff session; every action here reaches across every organization deliberately.

### 1.1 Organization & institute provisioning
Creates an `Organization` (one paying customer) and its first `Institute` (one branch/campus — the actual tenant-isolation boundary; an org can own several) in one request: name, code, address, an owner invite and/or an admin invite, and which of the six billable modules (Enquiry/Admission/Attendance/Fees/Payroll/Expense) start active. Each invite generates a temp password and sends a login email through the platform's global SMTP config (falls back to console-logging the credential if SMTP isn't configured, so nothing silently fails in dev). Institutes can also be added to an existing organization one at a time later, with their own admin invite.

### 1.2 Plans & per-institute limits
A `Plan` defines headcount caps per capped role (ADMIN/ACCOUNTANT/FACULTY/RECEPTION/STUDENT). Assigning a plan to an institute **snapshots** those numbers onto the institute itself (`maxAdmins`, `maxFaculty`, …) rather than the institute reading the plan live — editing a plan afterward never silently changes what an already-assigned institute is allowed. A SuperAdmin can also override one institute's snapshot directly ("this one customer needs 40 faculty") without touching the shared plan, and the UI shows a "customised" badge whenever an institute's live numbers have drifted from what its plan currently says. Module toggles (Enquiry/Admission/Attendance/Fees/Payroll/Expense) are per-institute switches independent of the plan; an unsubscribed module returns `403 MODULE_DISABLED` on every one of its routes regardless of role.

### 1.3 Institute suspension + history — §12.10
Suspending an institute (`isActive: false`) is the *only* way an institute is ever taken out of service — there is no delete anywhere in this codebase, by design, so fee/attendance/payroll history stays intact forever. Suspending now **requires a reason** (enforced server-side, 400 without one) and writes one `InstituteSuspension` row per cycle (`suspendedBy`, `suspendedAt`, and later `liftedBy`/`liftedAt` when reactivated — at most one open row per institute, since suspend/reactivate strictly alternate). The institute detail page shows the complete history: who suspended it, when, why, whether it's still in effect or when/by whom it was lifted. Suspension is enforced immediately, not on next login — `authenticate` checks live institute status on every single request, so an active session gets rejected mid-use.

### 1.4 Institute data export — §14.2
Two entry points, same underlying bundle: `GET /org/export` (self-service, OWNER/ADMIN, in Settings) and `GET /platform/institutes/:id/export` (SuperAdmin, audit-logged, placed in the institute detail page's Access card next to Suspend — the real use case is "get a copy before this institute is wound down"). Both stream a zip (via `archiver`, built on this session's `ZipArchive` class API) containing five CSVs generated fresh on each request — `students.csv`, `fee_installments.csv`, `payments.csv`, `attendance.csv`, `payroll_payments.csv` — each with real column headers, not raw DB field names. Nothing is pre-generated or cached; it's a live read straight through Prisma into `toCsv()`. A genuine loading state (spinner + "Preparing…") on both buttons, since a whole-institute export can take a few seconds. Institute *deletion* was explicitly **not** built alongside this — see §3 of `progress.md`.

### 1.5 Platform health dashboard — §14.1
`GET /platform/health` aggregates two tables that were already being written on every send attempt elsewhere in the app — `OutboundMessage` (WhatsApp: QUEUED/SENT/FAILED) and `MessageLog` (email: delivered boolean) — into a date-ranged report (defaults to the last 30 days): overall send counts and failure/bounce rate for each channel, plus a per-institute breakdown **sorted worst-first** by whichever channel is worse for that institute, so the institute most likely to need a call sits at the top rather than being buried alphabetically. Pure aggregation — no new tracking, no new writes. Deliberately does *not* include Cloudinary storage usage per institute (no file-size data is stored anywhere today; would need either a live third-party API call on every dashboard load or a backfill of every historical asset — flagged as an open question, not silently assumed) or general application error rates (this app has no error-monitoring tool wired up at all — a separate, larger gap).

### 1.6 Global search — §12.9
`GET /platform/search?q=` runs four searches in parallel — `Student` (name/email/phone/parentPhone), `User` (name/email), `Institute` (name/code), `Organization` (name/code) — each result tagged with the org/institute it belongs to, so "which institute is this phone number in" is answerable without guessing which organization to open first. Replaces what used to be a completely inert header search box (it accepted typing but queried nothing) with a working, 250ms-debounced, grouped-results dropdown that links straight to the relevant detail page. Requires at least 2 characters before it queries anything.

### 1.7 Audit log viewer — §12.7
`GET /platform/audit-log` reads `AuditLog` rows that four other route files were already writing (institute suspensions, forced logouts, MFA resets, team invites, module toggles, maintenance windows, data exports…) but that had no viewer anywhere before this. Filterable by institute (a real dropdown, not free text), action (substring match), and a date range; paginated (50/page) since this table only grows. Because `AuditLog.userId`/`organizationId`/`instituteId` are plain string columns rather than relations (deliberately — a log row has to survive the thing it references being deleted), actor/org/institute display names are resolved via one batched lookup per page rather than a join; a deleted user shows as "Deleted user" rather than breaking the row. Each row's `metadata` JSON is expandable inline for full detail.

### 1.8 Platform-wide user directory — §12.6
`GET /platform/users` lists every staff account (OWNER/ADMIN/ACCOUNTANT/FACULTY/RECEPTION) across every organization — name, email, role, institute, last login, and 2FA status — filterable by role or a name/email search. Built specifically as the surface for the MFA-disable escape hatch below, since no per-institute page shows FACULTY/RECEPTION at all, let alone across every institute.

### 1.9 Session revocation lever — §12.2
`POST /platform/users/:id/logout-everywhere` bumps that account's `tokenVersion` by one. Since every JWT carries the `tokenVersion` it was signed with, and `authenticate` compares it against the live column on every single request, this invalidates every existing session for that account **immediately** — no token blocklist, no per-token bookkeeping, just one integer comparison on a query that already runs. Audit-logged. The self-service equivalent (`POST /auth/logout-everywhere`, any role, from your own Profile page) uses the exact same mechanism, with the honest caveat that it logs the calling session out too (the confirm dialog says so up front) — and deliberately requires no password re-entry, since gating a "my session might be compromised" action behind the very credential that might be compromised is counterproductive.

### 1.10 MFA disable escape hatch — §12.6
`POST /platform/users/:id/mfa/disable` — the "I lost my phone *and* my backup codes" recovery path, which otherwise has no way back into the account at all. Requires a `reason` (400 without one) and is audit-logged with that reason attached, since this is itself a new attack surface: a compromised SuperAdmin account could use it to strip anyone's second factor before taking over. Clears `mfaSecret`/`mfaEnabledAt`/`mfaBackupCodes` in one update.

### 1.11 Help & Support triage queue — §12.3
`GET /platform/support/tickets` — every ticket filed by any staff member at any organization, filterable by status (OPEN/IN_PROGRESS/RESOLVED) and category (BILLING/BUG/FEATURE_REQUEST/OTHER), ordered open-and-oldest-first (the ticket most likely to have been forgotten surfaces at the top). A SuperAdmin reply auto-transitions OPEN→IN_PROGRESS; changing status is a separate explicit action. Since a `SupportTicket` is scoped to an **organization**, not an institute (an OWNER can file one before ever entering a specific institute), the platform side sees the org and, when set, which institute the ticket is actually about. SuperAdmins can't receive the in-app `Notification` row a naive design would assume (that model's `instituteId` column is required, and SuperAdmins have none) — resolved by relying on the queue itself as their inbox plus an email fallback to `SUPERADMIN_EMAIL` on every new ticket and every institute-side reply.

### 1.12 Maintenance mode — §12.11
`MaintenanceWindow` (scope: GLOBAL or one INSTITUTE) with a start time, end time, and a required reason. Status (`upcoming`/`active`/`ended`/`cancelled`) is never stored — `lib/maintenance.ts`'s `deriveStatus()` computes it live from the timestamps versus now, the same "derive, don't store" rule every other status field in this app follows, backed by a 15-second in-process cache that's invalidated immediately on any write so a schedule/cancel takes effect without a stale read. `authenticate` calls `getBlockingWindow()` on every request from a non-SUPERADMIN account and rejects with `503 MAINTENANCE_ACTIVE` (carrying the reason and end time) while a window is genuinely active right now — the exact same choke point session revocation and institute suspension use, so a maintenance window can't be bypassed by an already-open tab any more than those can. Scheduling rejects overlapping windows within the same scope. A pre-start countdown banner (`getNoticeWindow()`, preferring an active window over the soonest upcoming one) warns staff before it actually starts. Every schedule/cancel is audit-logged.

### Not built at the platform layer

- **Multi-institute analytics rollup** (§12.4) — combining an org's institutes into one analytics view. Nothing blocking; only useful once an org actually has 2+ institutes to look at together.
- **Impersonate / "view as"** (§12.8) — a SuperAdmin viewing the app exactly as a specific OWNER/ADMIN sees it. Deliberately gated on explicit sign-off before any code: a compromised SuperAdmin account plus impersonation is a compromise of every institute on the platform, and the plan's own read-only-by-default + dual-identity-audit design needs to be agreed on first.
- **Billing/invoicing view** — there is no mechanism yet for the platform to actually charge an institute; `Plan` is a label, not a payment relationship. A billing screen today would show nothing real.
- **Bulk institute operations** (e.g. "extend every trial institute by 7 days") — there's no self-serve trial/signup flow yet to make "bulk" mean anything; every institute is manually onboarded one at a time.
- **Institute data deletion** (§14.2) — blocked on an actual policy answer to "what does deleted mean" (hard-delete vs. anonymize-but-keep-financial-history vs. export-then-purge), not on engineering effort.

## 2. Institute / staff layer (OWNER / ADMIN / ACCOUNTANT / FACULTY / RECEPTION)

Every route here is scoped by `req.tenantId`, stamped by `requireInstitute` middleware from the authenticated token — never trusted from a request body or param — so cross-institute access is structurally impossible, not just policy.

### 2.1 Enquiries → Admissions → Students

- **Enquiry pipeline** (`enquiry.ts`) — new → contacted → converted → lost, with a source field and a per-enquiry activity/follow-up trail. Reception/front-office roles, faculty deliberately excluded.
- **Admissions** (`admission.ts`) — admit a student directly, or convert an open enquiry (which flips it to CONVERTED and logs the conversion activity). Assigns course + batch in the same action; auto-generates a deterministic student code and a placeholder email if none is given.
- **Bulk CSV import** (§12.1) — `POST /students/import` and `POST /org/team/import`, both **validate-then-commit**: every row is checked (required fields, course/batch codes resolved, duplicate detection) before any database write, with a dry-run preview mode that writes nothing and shows exactly what would happen, then a confirm step that commits. The per-row report accounts for every single row as created/skipped/error, never a bare success count. Re-uploading the same file is idempotent — already-created rows are recognized and skipped, not duplicated (including rows with no email, which get an auto-generated one each time; a `(courseId, phone)` fallback key was specifically added to catch this case after a real bug surfaced it during testing). A downloadable CSV template with the exact expected column headers, and a "download error report" for just the failed rows.
- **Student directory** (`students.ts`) — full CRUD, search/filter by course/batch/status, roster export as CSV/print, subject-wise enrollment management for courses priced per-subject rather than flat.
- **Self-service admission form** (§8f, `public.ts`) — an unauthenticated, PIN-protected public link where a pre-created student fills in their own remaining details once; rate-limited, generic failure messages to prevent enumeration.

### 2.2 Academics & attendance

- **Courses, subjects, batches** (`academics.ts`) — full CRUD. A course's `feeMode` (FLAT or SUBJECT_WISE) and fee structure become locked once it has enrolled students or a fee account, to prevent retroactively invalidating what students already agreed to pay.
- **Faculty teaching assignments** — which courses/subjects a given faculty member is authorized to teach; used to gate who can be picked as an invigilator or lecture teacher.
- **Lecture scheduling + attendance** (`attendance.ts`) — schedule a lecture for a batch+subject+faculty, mark a whole roster in bulk (PRESENT/ABSENT/LEAVE/HOLIDAY, either manually or via a biometric device's `POST /attendance/scans` with device-key auth), a daily summary view, and CSV export.
- **Tests** (`tests.ts`) — a test is modeled as a special kind of lecture session (`kind: TEST`), so it inherits the same scheduling/conflict-checking machinery; requires an invigilator, supports uploading a question paper (Cloudinary, public visibility — course material, not a financial document), and a dedicated marks-entry flow per session that only accepts scores for students marked present. A per-session report shows the full roster with pass/fail stats.

### 2.3 Fees & payments

- **Fee accounts & installments** (`fees.ts`) — one `FeeAccount` per student, `finalFee = courseFee − discount`; installments auto-split with a monthly gap, the last one absorbing any rounding remainder. Staff can reschedule a due date, waive an installment, or reprice — each with guardrails once real payment history exists against it.
- **One single payment-writing path** — `applyPayment()` is the *only* function anywhere in the codebase that ever creates a `Payment` row or touches `FeeInstallment.paidAmount`, whether the money came from a manual entry, a proof approval, or (in the future) any other source — it handles receipt numbering, waterfall allocation across open installments, and carry-forward when a payment settles an installment short. This was a deliberate architectural rule specifically to prevent two payment paths ever disagreeing.
- **Defaulters list** — every student currently overdue, with how much and since when.
- **Receipts** — every payment gets a `receiptNumber` (gapless per-institute-per-month sequence) and, this session, a genuinely redesigned document: a shared letterhead/meta/itemized-table/totals/footer layout used identically by the in-app receipt modal and the **public, unauthenticated share link** (`/r/[token]`) a parent can open straight from a WhatsApp message — printable, revocable, and now correctly showing a VOID stamp that doesn't overlap the document title (a real layout bug found and fixed during this session's live browser verification).
- **Self-serve UPI collection** (§13.1, replacing an earlier uploaded-QR design) — `InstitutePaymentConfig` now holds only a UPI ID, payee name, and instructions; no image is ever uploaded or stored. Both the student portal and the settings preview render a QR **generated live in the browser** (via `qrcode`, drawn to a canvas, downloadable) from the exact same `upi://pay?…` string builder (`lib/upi.ts`) the tap-to-pay deep-link button reads from, so the two can never disagree — and the amount is baked into the QR only when one is actually entered, leaving it an open-amount scan otherwise. Enabling payments now requires a UPI ID (an uploaded QR alone used to be sufficient; no longer possible since there's nothing left to upload).
- **Payment-proof approval** (`PaymentProof`) — a student submits a claimed amount + a screenshot (compressed client-side before upload) + optional UPI reference; staff review and approve, which routes through the same `applyPayment()` — a screenshot is treated as a claim, never a receipt, exactly per the schema's own doc comment.

### 2.4 Payroll

- **Salary profiles** (`SalaryProfile`) — FIXED (monthly rate) or PER_LECTURE (per-session rate), for either a platform login (a real staff User) or an external payee with no login at all (name/email/phone only, for notification purposes).
- **Payroll ledger** — per-period earnings broken into `PayrollLineItem` rows (one per fixed-salary period, one per taught lecture for per-lecture staff), each tracking its own paid/outstanding amount independent of the others.
- **Payroll runs** (`PayrollRun`) — one per institute-per-month, a status+approval wrapper (Draft → Approved → Paid) over line items that are always derived, not duplicated into the run itself.
- **Bulk "pay remaining balance"** — settle everything outstanding for a staff member (or a whole run) in one action, with the same waterfall-plus-advance-credit allocation logic as fee payments.
- **Real payslip documents** — built from scratch this session; there was no formatted payslip anywhere in the product before this, only a WhatsApp-style text confirmation of a single payment transaction (which still exists, distinctly, renamed from "Payslip" to "Notify"/"Payment confirmation" once a real payslip existed to avoid the two being confused). The actual payslip documents one full pay period — institute letterhead, staff name/designation, an itemized earnings table with each line tagged Paid/Partial/Unpaid, gross/paid/net totals — using the exact same shared document-layout components as receipts, with its own accent color so the two document types are visually distinct even in black-and-white print.
- **Staff leave requests** (`LeaveRequest`) — a staff member's own time-off request, deliberately with **no automatic effect on pay** yet (a FIXED salary is unaffected by a leave day; PER_LECTURE pay is already zero for a day nothing was taught) — whether unpaid leave should deduct from a FIXED salary is an explicitly unresolved policy question, not an oversight.

### 2.5 Money, ops & communication

- **Expenses** (`expenses.ts`) — categories (seeded with a standard default set per new institute, then customizable), events for tagging a batch of expenses together, and every expense/income feeding into a combined `FinanceEntry` ledger with CSV export.
- **Distribution tracking** (§8e) — hand out physical items (books, bags, kits) with an eagerly-created per-student `DistributionReceipt` the moment a new student is admitted into a course with active distribution items, plus a bulk "mark received" roster action for staff.
- **Parent-teacher meetings** (§11.2) — per-batch scheduling, reschedule/cancel, a copy-to-WhatsApp message generator (one shared vars-builder function, reused everywhere a PTM message is composed, after a real bug where an omitted `{{venue}}` variable once rendered literally in a live message), and automated reminders on two fixed lead times.
- **WhatsApp + email dispatch** — per-institute WhatsApp Business Cloud config (encrypted access token at rest) with template sync/draft/submit against Meta's API, per-institute SMTP override (falling back to the platform's global config), and one `OutboundMessage`/`MessageLog` row per attempt on either channel — the data this session's platform health dashboard reads.
- **Staff-only scheduled reminders** (`ScheduledReminder`, §8d) — dated obligations like "renew the fire safety certificate," with configurable lead times and repeat rules, a genuinely separate system from student-facing notifications (`studentNotify.ts`) despite sharing the word "reminder" — the two have different schedulers, different audiences, and are never to be conflated.
- **Study material library** (§12.5, built this session) — a `StudyResource` is scoped to a **course**, not a batch (confirmed as the right call: the same notes serve every batch of a course, so batch-scoping would just mean duplicated uploads drifting out of sync), with an *optional* subject — course-wide material like a syllabus PDF genuinely belongs to no single subject. Either a file (Cloudinary, public visibility, magic-byte validated) or an external link (YouTube, Drive, Zoom recording). Deleting a resource removes the Cloudinary asset, not just the database row. Gated to OWNER/ADMIN/FACULTY — the same bar as scheduling a lecture or test; RECEPTION is deliberately excluded as this is course content, not front-desk work.

### 2.6 Team & settings

- **Team management** — invite ADMIN/ACCOUNTANT/FACULTY/RECEPTION with temp-password emails, plus the same bulk-CSV-import treatment as students (§12.1), including per-role headcount capacity checks during import so a bulk file can't silently blow through the plan's limits.
- **Portal access issuance** (§10.6) — turning on `Course.portalEnabled` and then explicitly issuing a login per student (or bulk-issuing for a whole course) is the *only* way a student ever gets a login — never automatic at admission. Re-issuing detects when a student has moved to a course the current credential wasn't issued for.
- **Institute settings** — profile (name/address/contact), module status (read-only here — toggled only by the SuperAdmin), UPI payment config with a live QR preview, WhatsApp/email config, and the data-export button described in §1.4.
- **MFA / two-factor authentication** (§12.6, built this session) — opt-in TOTP for every staff role (OWNER/ADMIN/ACCOUNTANT/FACULTY/RECEPTION — deliberately expanded from an original OWNER/ADMIN-only plan, confirmed with the user before building). Setup shows a real QR code (server-generates the secret, encrypts it at rest with the same helper used for WhatsApp tokens, returns a scannable QR + a manual-entry fallback code); confirming with a valid 6-digit code enables it and shows **ten one-time backup codes exactly once**. Login for an MFA-enabled account becomes two steps: password first (returns a short-lived challenge token, not a session), then a TOTP or backup code to actually get a session. A used backup code is removed from the account immediately so it can never be replayed — verified live during this session's build.
- **Session controls** — "Sign out of all devices" in Profile → Security, using the same `tokenVersion` mechanism as the platform-side lever.
- **Help & Support** — a Help icon in the header (next to notifications), opening a drawer to file a new ticket or continue a threaded conversation with the platform — the staff-side half of §1.11.
- **Analytics** (`analytics.ts`) — enrollment, attendance, test performance, and fee/payroll figures, filterable by date range/course/batch, OWNER/ADMIN only (the same bar as Fees and Payroll themselves, since it surfaces those figures).

## 3. Student portal (`/portal/*`)

A structurally separate app — its own layout tree, its own `RoleRoute` gate, and every single read in `portal.ts` scopes to `req.user.studentId` (stamped by `authenticate` from the student's own linked row at login) rather than any id in the request URL, which is what makes it impossible for one student to ever read another's data by tampering with a request.

- **Dashboard** — attendance rate, up to 3 upcoming lectures/tests, up to 3 recent results, fee summary, unread notification count, in one round trip.
- **Timetable** — upcoming lectures for their current batch (derived from their most recent, still-active `StudentBatch` row).
- **Tests & results** — marks as staff enter them, with the test's total marks for context.
- **Attendance** — their full attendance history and computed rate (HOLIDAY days excluded from the denominator, LATE counted as present — matching exactly how the staff-side summary computes the same number, so the two views can never disagree).
- **Fees** — installment status and balance (derived live from the same rules the staff view uses, never a separately-stored status), payment history with links to the same public receipt pages staff generate, and a **Pay fees** sheet: a live UPI QR + tap-to-pay button (mobile only, since it's a dead button without a UPI app) prefilled with what's actually due, and a payment-proof submission form (amount, optional UTR, a compressed screenshot) that lands in the staff approval queue.
- **Study material** — everything shared for their own course, grouped by subject with course-wide material shown last. The nav item itself is **hidden entirely** until their course actually has something in it — driven by a `hasStudyResources` flag computed fresh on every `/auth/me` call, specifically so a student never taps into a guaranteed-empty page.
- **Notifications** — every student-facing event (fee reminders, test results, attendance marks, PTM notices, lecture changes…) with a type-specific deep link into the exact right portal screen, rendered through one shared function per channel so in-app and WhatsApp wording can never drift apart the way a real prior bug once let them.
- **Portal login** — see §2.6; never automatic, always an explicit staff action per student.

## 4. Cross-cutting infrastructure

Nothing here is a page anyone visits, but every feature above depends on it.

- **Authentication** — JWT bearer tokens (kept in `localStorage`, not cookies — a deliberate architectural fact that shaped the decision *not* to build the Web Share Target feature in §13.2, since a raw browser POST can't carry a token stored this way). Sliding-expiry sessions: a token silently renews itself once it's more than halfway to its own expiry, but stops renewing once the *original* login is more than 14 days old, so a session has a real ceiling rather than living forever on a rolling token. `authenticate` re-validates account status, institute suspension, portal eligibility, `tokenVersion`, and now maintenance-window blocking on **every single request**, not just at login — which is what makes revoking access by any of those mechanisms take effect on the very next request rather than whenever a token happens to expire naturally.
- **Tenant isolation** — every operational query filters by `req.tenantId`, itself stamped only from the verified JWT, never from anything client-supplied.
- **File uploads** (`services/uploads.ts`) — one shared module for every upload in the app (test papers, payment proofs, study material). Validates real file type by magic bytes, never trusting a client's declared MIME type. Decides `public` vs `authenticated` visibility per file type deliberately: course material gets a public, unguessable Cloudinary URL (acceptable exposure, like a notice-board poster); financial documents (payment-proof screenshots) get `authenticated`, requiring a signed, short-lived URL — a distinction that mattered in practice, since an early version of the payment-proof feature stored a URL that embedded a permanent signature and defeated the whole point, caught by testing before it shipped.
- **Notifications** (`studentNotify.ts`) — `notifyStudent()`/`notifyBatch()` are the only functions that ever write a student-facing in-app `Notification` row, fire a push notification, and dispatch WhatsApp — rendering the message body once and reusing it for every channel, and skipping the in-app channel entirely when portal access isn't currently active.
- **PWA** — installable on any device including iOS (Add to Home Screen), an offline-capable app shell via a service worker (deliberately guarded to only register in production builds — service workers and Next.js's dev-mode Fast Refresh actively conflict, which was diagnosed and fixed this session after it produced a confusing "ServiceWorker script evaluation failed" console error), and web push (functional on iOS 16.4+ once installed).
- **Rate limiting** (`middleware/rateLimit.ts`) — a shared per-IP sliding-window limiter applied to every unauthenticated or abuse-prone surface: login, forgot-password, OTP verification, the self-fill admission form, and MFA code verification (a 6-digit TOTP code has a much smaller guess-space than a password, so this one is deliberately tight).
- **Encryption at rest** (`lib/crypto.ts`) — AES-256-GCM, one shared helper used for both WhatsApp Business access tokens and MFA secrets, so there's exactly one encryption pattern in the codebase to reason about rather than two.
- **Audit logging** (`services/audit.ts`) — one shared `auditLog()` call, used by every SuperAdmin-side mutation (suspensions, forced logouts, MFA resets, data exports, maintenance scheduling) and viewable through §1.7.
- **Role-based route gating** — `RoleRoute`, now applied to every section in the app (added this session — previously most sections relied purely on the sidebar hiding a link, with the actual page rendering and failing on every API call if visited directly by URL). A role-mismatched visit now redirects to a real `/forbidden` (403) page rather than either a silent redirect or a page full of failed requests.
- **404 / 403 pages** — both built this session: a full-bleed, on-brand page for each (reusing the same textured brand background as the login screen), rather than a bare browser error or Next.js's default.
- **App-wide scrollbar & theme polish** (this session) — a global thin, auto-hiding scrollbar (visible only on hover, via CSS alone) applied to every scrollable element in the app without needing a class on each one; the dark-mode toggle moved out of the header into the profile dropdown, since it's an account preference, not a primary navigation action.

## 5. What's deliberately not built (see `progress.md` §3 for the full reasoning)

| Item | One-line reason |
| --- | --- |
| Multi-institute analytics rollup (§12.4) | Nothing blocking — no org has 2+ institutes to test it against yet. |
| Impersonate / "view as" (§12.8) | Highest-blast-radius item in the product; needs explicit sign-off before any code. |
| Web Share Target for payment proofs (§13.2) | Android-only, undocumented share format, needs new plumbing purely to work around `localStorage`-based auth — narrow payoff versus the manual upload path that already covers every device. |
| Institute data deletion (§14.2) | No real delete exists anywhere in this codebase yet; needs a policy answer first, not code. |
| Automatic fee-overdue sweeps | Needs a policy decision on trigger schedule/threshold. |
| Unpaid-leave payroll deduction | Needs a policy decision: full-pay-regardless vs. per-day deduction. |
| Billing/invoicing view | The platform has no mechanism to actually charge an institute yet. |
| Bulk institute operations | No self-serve trial/signup flow exists to make "bulk" meaningful yet. |
| Audit log CSV export | Currently view-only; fine until the first real compliance/legal request for it. |
| Support ticket SLA/stale-ticket notification | The queue shows ticket age; nothing proactively pings anyone yet. |
